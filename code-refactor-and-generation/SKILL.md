# 代码重构及生成

在批准的范围内保持项目目录精简和算法行为等价。生成新代码前，先确认模型任务、算法和数据接口。以真实代码、配置和数据约定为依据。

## 先检查，再提交修改计划

1. 确认目标项目根目录，读取现有目录、源代码、配置和数据划分文件，确认实际方法编号及各方法使用的数据集。参照[项目结构与运行配置](references/project-layout.md)确定路径，并按[预处理、固定划分与训练](references/data-and-training.md)执行一次性只读 Python 检查。终端汇报发现，缺失和异常记入计划。
2. 在项目根目录生成 `修改计划.md`。每次新任务可覆盖旧计划。计划写明本次目标和范围、现状与问题、拟新增/修改/删除的文件及原因、实施步骤、风险与影响、验证方式和当前确认状态。用一个 `text` 代码块按实际确认的方法编号给出预期完整项目结构，标明变更文件和拟删除项。示例中的方法 1 和方法 2 用来说明命名。
3. 在 `修改计划.md` 末尾设立 `## 待确认问题`，作为最后一节。所有需要用户决定或确认的问题集中放在这一节，按编号逐条列出。将未确定的方法数量或编号、模型接口、划分表字段、固定划分来源或联合训练/评估策略逐项列为待确认，给出可行选项。额外文件、目录或层级也需说明必要性并列入待确认项。
4. 提交计划后暂停，等用户明确批准。等待期间仅按反馈更新计划。代码、数据、配置和实验产物的改动，以及有写入的运行检查，都在批准后进行。已批准同一份计划时直接实施。遇到超出计划的文件或需求、新的未知风险或待确认问题，更新计划并等待对变更范围的批准。

## 按阶段实施

- 获批后按[项目 Conda 环境](references/project-layout.md#项目-conda-环境)将运行依赖安装到项目根目录的 `environment/`。从项目根目录用 `conda activate ./environment` 激活。
- 使用[项目结构与运行配置](references/project-layout.md)核对入口、各阶段 `config.yaml` 和允许写入的位置。只为实际确认的方法 N 建立对应入口、配置和输出目录，保留 `evalutionN/` 的原拼写。编号对应方法，示例产物用于说明命名。
- 涉及预处理、划分表、训练或断点续训时，阅读[预处理、固定划分与训练](references/data-and-training.md)。方法 N 绑定 `processCodeN.py`、`processN/` 与 `trainCodeN.py`。原始数据保持只读。Excel 划分表 按实际使用的组合命名为 `datasetMSplit-processN.xlsx`。训练沿用各数据集的固定划分，只用验证集选择 `best`。
- 涉及评估、推理或其输出时，阅读[评估、推理与结果保存](references/evaluation-and-inference.md)。从明确指定的 Checkpoint 恢复模型结构，沿用同编号的预处理数据。最终评估只用固定测试集。写入前检查本次全部目标名，遇到冲突停止写入。
- 所有预处理、训练、测试集评估和推理入口运行时，都必须在控制台显示随实际处理进度更新的进度条。进度条标明当前阶段，并显示已完成数量、总量和处理单位。总量无法预先确定时，显示当前已处理数量。
- 预处理显示当前数据集及样本进度。训练显示当前 Epoch 和该 Epoch 内的 Batch 进度。测试集评估与推理显示当前数据集及已处理的样本数或 Batch 数。
- 在现有脚本内部整理函数和类。保持模型、损失、预处理顺序、训练策略、划分、推理逻辑和现有调用行为，除非对应行为变更已获批准。各阶段通过自身的 YAML 配置参数，支持直接运行入口。遵守历史实验结果和 Checkpoint 的保留规则。

## 验证与交付

按[静态审查与最小运行检查](references/verification.md)先审查实现，再对已批准且可安全执行的阶段做小规模入口检查。核对临时修改的配置已恢复原始内容。按清单报告通过、失败、未验证及原因；将范围外的项目标为不适用。报告范围以实际执行的静态审查和运行检查为准。
